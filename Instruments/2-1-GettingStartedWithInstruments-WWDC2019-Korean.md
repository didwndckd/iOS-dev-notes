# Getting Started with Instruments — WWDC19 한국어 자막 번역

- 영상: [Apple WWDC19 · Getting Started with Instruments](https://developer.apple.com/kr/videos/play/wwdc2019/411/)
- 발표자: Tibet Rooney-Rabdau, Ben Mitchell, Anand Subramanian
- 번역 원문: 사용자가 제공한 영어 자막 전문
- 번역일: 2026-10-18
- 타임스탬프는 제공된 자막을 유지했다. 명백한 음성 인식 오류는 문맥에 맞게 보정했다. UI와 기능 설명은 발표 당시인 2019년 기준이다.

**0:00**

좋은 아침입니다. 「Getting Started with Instruments」에 오신 것을 환영합니다. 저는 Tibet Rooney-Rabdau이고, 오늘은 팀 동료인 Ben Mitchell, Anand Subramanian과 함께합니다.

**0:25**

훌륭한 사용자 경험을 제공하는 일을 생각하면, 저는 가장 먼저 성능을 떠올립니다.

**0:32**

응답성은 사용자와 앱 사이에 신뢰를 쌓아 줍니다. 앱의 UI가 아무리 마음에 들어도, 돌아가는 대기 표시를 보거나 배터리가 빨리 닳으면 앱에 대한 전반적인 경험은 나빠집니다.

**0:47**

앱에서 훌륭한 사용자 경험을 만들려면 이런 측면을 기억해야 합니다. 오늘 세션에서는 저희가 성능 측정에 즐겨 사용하는 도구인 Instruments를 소개하겠습니다. Instruments를 처음 접하거나 개발 작업 흐름에 더 잘 통합하고 싶은 분들에게 적합한 세션입니다.

**1:07**

성능은 개발 초기부터 자주 측정하는 것이 중요합니다. 개발 주기 어느 시점에서든 성능 저하가 생길 수 있고, 그 영향이 누적될 수 있기 때문입니다. 저는 Xcode와 Instruments를 가장 친한 친구라고 생각합니다. 그래서 Dock에서도 Instruments를 Xcode 옆에 둡니다. 개발 과정 내내 일찍부터 자주 프로파일링해야 한다는 사실을 상기하기 위해서죠. 오늘은 먼저 Instruments와 그 기능을 소개하고 사용자 인터페이스를 둘러보겠습니다.

**1:35**

이어서 앱을 프로파일링해 여러 작업에 걸리는 시간을 측정하는 방법을 보여 드리겠습니다. Time Profiler라는 도구로 앱이 어떤 작업을 얼마나 수행하는지 알아보겠습니다. 마지막으로 앱의 동작을 파악할 수 있도록 Signpost를 추가하는 방법을 설명하겠습니다.

먼저 Instruments를 살펴보겠습니다. Instruments는 Xcode 도구 모음에 포함된 강력한 성능 분석 및 테스트 도구입니다. iOS, macOS, watchOS, tvOS 등 모든 플랫폼의 앱을 프로파일링해 동작과 성능을 더 잘 이해하고 최적화할 수 있습니다.

**2:16**

Instruments는 개발, 테스트, 디버깅 과정에서 사용할 수 있습니다. 좋은 소식도 있습니다. Xcode가 있다면 Instruments도 이미 설치되어 있습니다. Xcode의 Product 메뉴에서 Profile을 선택하면 됩니다.

Instruments는 Xcode에 포함되어 있고 함께 사용하는 경우가 많지만, 필요하면 독립적으로 사용할 수 있는 별도 앱입니다. 성능 분석을 어떻게 시작할지는 자유롭게 선택할 수 있습니다. 이제부터는 Instruments라는 단어를 두 가지 의미로 사용하겠습니다.

**2:45**

지금까지는 Instruments 앱을 이야기했습니다. 왜 이런 이름일까요? 앱의 여러 영역을 프로파일링하는 Instrument라는 도구들을 제공하기 때문입니다.

**2:55**

어느 쪽을 가리키는지 혼동될 만한 곳에서는 애플리케이션을 ‘Instruments 앱’이라고 부르겠습니다.

**3:02**

개별 Instrument는 앱, 프로세스, 운영체제의 중요한 부분에 삽입된 기반 기능을 통해 시계열 추적 데이터를 수집합니다.

**3:11**

Instrument가 수집하는 데이터를 트레이스(trace)라고 부르기도 합니다.

**3:15**

여기 제가 좋아하는 Instrument 두 개가 있습니다. 왼쪽의 Time Profiler는 운영체제가 제공하는 기반 기능을 이용해 관련 스레드의 호출 스택을 일정한 간격으로 수집합니다.

**3:27**

오른쪽의 Points of Interest는 Signpost API 같은 여러 API로 표시한 앱의 중요한 영역에서 데이터를 수집합니다.

Instruments를 처음 열면 Pages나 Numbers 문서에서처럼 템플릿 목록이 표시됩니다. 템플릿은 성능에 관한 질문에 답할 수 있도록 미리 구성된 Instrument 모음입니다. Pages의 생일 카드 템플릿이 생일 카드를 만드는 데 필요한 문서 구조를 제공하는 것과 비슷합니다.

이 짧은 세션에서 모든 템플릿을 다루기는 어려우므로 Time Profiler 템플릿에 집중하겠습니다. 이 템플릿에는 방금 소개한 Time Profiler와 Points of Interest를 비롯한 여러 Instrument가 들어 있습니다.

**4:07**

이 도구들은 앱의 응답성과 자원 사용을 이해하는 데 유용합니다. Time Profiler 템플릿을 처음 열면 프로파일링할 준비가 된 빈 문서가 표시됩니다. 오른쪽 위의 Add Instruments 버튼을 클릭하면 문서에 Instrument를 추가할 수 있습니다.

**4:27**

그러면 Instruments 앱이 사용 가능한 Instrument 전체 목록을 담은 라이브러리 팔레트를 표시합니다.

**4:33**

여기서 새로운 Instrument를 찾아 문서로 드래그하면 더 많은 데이터를 수집할 수 있습니다.

**4:39**

왼쪽 위에는 프로파일링 제어 버튼이 있습니다. 데이터 수집을 녹화하거나 일시 정지하거나 중지할 수 있습니다. 그 옆에는 대상 선택 영역이 있습니다. 왼쪽의 대상 기기 목록에서는 프로파일링할 기기를 선택합니다. 기기와 그 기기에서 프로파일링할 프로세스를 선택하는 Xcode의 대상 선택 영역과 비슷합니다.

**5:01**

보통은 앱의 프로세스를 대상 프로세스로 선택합니다. 하지만 공유 확장 프로그램을 프로파일링한다면 앱과 별도 프로세스로 실행되는 확장 프로그램의 프로세스를 선택해야 합니다.

Time Profiler 템플릿에서 녹화를 시작하면 문서에 트레이스 데이터가 채워집니다. 참고로 Instruments의 녹화도 앱처럼 시스템 자원을 사용합니다. 앱에 미치는 영향을 줄이기 위해 Instruments는 Last Few Seconds Mode, 또는 Windowed Mode라는 기능도 제공합니다.

**5:31**

Windowed Mode에서는 녹화가 끝날 때까지 결과를 분석하거나 표시하지 않으며, 녹화 종료 직전 몇 초보다 앞선 이벤트는 무시합니다. 녹화를 시작해 두었다가 문제가 보일 때 중지하고 싶은 경우에 유용합니다. 짧은 시간에 많은 데이터를 수집하는 일부 템플릿은 이 모드를 기본으로 사용합니다.

**5:51**

Time Profiler 템플릿에서 녹화를 마쳤더니 창의 여러 영역에 많은 트레이스 데이터가 채워졌습니다. 복잡해 보일 수 있으니, 잠시 각 영역의 역할을 살펴보겠습니다.

**6:03**

창 위쪽에는 Track Viewer가 있습니다. 트랙은 프로세스, 스레드, CPU 코어처럼 하나의 이벤트 발생원에 해당하는 시계열 트레이스 데이터를 보여 줍니다. 하나의 Instrument가 여러 트랙에 데이터를 제공할 수도 있습니다.

이 예에서는 트랙 세 개가 보입니다. 맨 위 트랙은 Time Profiler가 제공하는 앱의 CPU 사용률 요약입니다.

**6:27**

다음 트랙은 Points of Interest가 수집한 데이터를 보여 줍니다. 이 부분은 나중에 Anand가 설명할 예정입니다. 그 아래에는 더 세밀하게 나눈 트랙들이 이어집니다. 하나의 Instrument가 만든 트레이스에 수십 개의 트랙이 있을 수도 있습니다.

**6:41**

트랙 필터를 이용하면 Instrument만 표시하거나, 스레드별 또는 CPU 코어별로 나누어 볼 수 있습니다. 이름으로 트랙을 검색해 더 구체적으로 찾을 수도 있습니다.

창 아래쪽의 Detail 뷰에서는 선택한 트랙의 트레이스 데이터를 살펴볼 수 있습니다. 이 예에서는 Time Profiler 트랙을 선택했으므로 트레이스가 기록되는 동안 각 스레드에서 호출된 함수를 탐색할 수 있습니다. Detail 뷰 오른쪽의 Inspector에는 Extended Detail 뷰가 있습니다.

**7:09**

이 뷰는 현재 맥락과 선택 항목에 따라 사용 중인 Instrument의 더 풍부한 정보를 제공할 수 있습니다. 여기서는 Time Profiler를 사용하고 있으므로 가장 큰 비중을 차지한 호출 스택이 요약되어 있습니다.

특정 시점에 무슨 일이 일어났는지 확인하는 또 다른 방법은 Inspection Head입니다. 트레이스의 특정 시점에 놓아 그때 발생한 모든 기록된 이벤트나 구간을 선택하는 표시자입니다. 선택한 이벤트의 추가 정보는 마우스를 올렸을 때 나타나는 레이블에 표시됩니다. 해당되는 경우 Detail과 Extended Detail 뷰도 선택한 이벤트의 정보에 맞춰 갱신됩니다.

**7:48**

이제 잠깐의 둘러보기를 마쳤고 Instruments의 사용자 인터페이스를 좀 더 이해하게 되었습니다. 창에 표시된 모든 내용은 트레이스 문서의 일부입니다. 트레이스 문서에는 프로파일링용으로 설정한 Instrument, 수집한 데이터, 결과 분석에 사용하는 뷰가 들어 있습니다.

**8:05**

Instruments 앱에서는 트레이스 문서를 저장했다가 다시 열 수 있습니다. 이전 결과를 살펴보거나 동료에게 공유해 함께 조사할 수 있죠.

이제 동료 Ben Mitchell을 무대로 모시겠습니다. 방금 소개한 기능을 실제로 사용하는 모습을 보여 드릴 겁니다. 감사합니다!

**8:37**

작년 WWDC2018의 일부 세션을 보셨다면 Solar System 앱을 기억하실 수도 있습니다. 약 1년 전에 출시했고 고객에게서 좋은 의견을 받았습니다. 하지만 좋지 않은 의견도 있었는데, 특히 성능에 관한 것이었습니다.

고객들은 특히 구형 기기에서 응답성 문제가 있다고 알려 주었습니다. 세션 전에 그중 하나를 재현할 수 있었습니다. 지금 Instruments를 연결한 상태로 보여 드리고, 문제를 해결할 수 있는지 살펴보겠습니다. 바로 시작하죠.

앱은 이미 실행 중이므로 Instruments만 열겠습니다.

**9:10**

이전에 사용했기 때문에 템플릿 선택 창에서 Time Profiler가 이미 선택되어 있습니다. Time Profiler는 특정 시간 구간에 발생하는 문제를 살펴보기에 좋은 도구입니다. Time Profiler를 선택하고 Choose 버튼을 눌러 새 트레이스 문서를 열겠습니다.

Xcode에서 실행한 것이 아니므로 먼저 추적할 프로세스를 선택해야 합니다.

**9:31**

대상 선택 영역에서 All Processes를 클릭하고 실행 중인 Solar System Mac 앱을 선택하겠습니다. 오른쪽에 숫자가 보입니다. 프로세스 식별자이며 활성 상태 보기에서도 확인할 수 있습니다. 앱을 선택했으니 창 왼쪽 위의 Record를 누르겠습니다.

**9:52**

**9:56**

Solar System 앱은 여러 트랙패드 제스처를 지원합니다. 클릭과 드래그뿐 아니라 이동, 손가락을 오므리거나 벌려 확대·축소하는 동작 등도 지원합니다.

고객들의 보고에 따르면 이런 동작을 하다가 Command + R을 눌러 데이터를 다시 불러오면 UI가 멈추고, 보기 싫은 회전 대기 커서가 나타납니다. 다른 이름으로 알고 계실 수도 있겠네요. 좋은 상황은 아니죠. 재현했으니 Instruments로 돌아가 무엇을 찾을 수 있는지 보겠습니다.

**10:23**

앱을 종료하면 Instruments의 녹화도 자동으로 멈춥니다. 여기에 수집된 트레이스 데이터가 보입니다. 먼저 더 자세히 볼 수 있도록 조금 확대하겠습니다.

**10:35**

마우스 커서를 트랙 영역에 놓고 핀치 확대 제스처를 하면 더 크게 볼 수 있습니다.

**10:42**

트랙 영역 왼쪽을 보면 여러 Instrument가 트랙을 제공하고 있습니다. Time Profiler는 CPU 사용률 요약을 보여 줍니다. Points of Interest는 아직 비어 있습니다. 나중에 Anand가 설명할 겁니다. 온도 상태 등 다른 트랙도 있고, 스크롤하면 더 세부적으로 나눈 트랙도 있습니다.

**11:00**

CPU 사용률 요약 트랙에 마우스를 올리면 사용률을 나타내는 레이블이 표시됩니다.

**11:08**

이 큰 영역에 도달하면 사용률이 100%를 넘습니다. 수상해 보이네요. 데이터를 다시 불러온 시점이 여기쯤일 것 같습니다. 다른 트랙과 비교해 보고 싶습니다.

그래서 Track Pinning이라는 기능을 사용하겠습니다. 창 왼쪽에서 트랙 항목에 마우스를 올리면 더하기 버튼이 나타납니다.

**11:31**

클릭하면 해당 트랙이 트랙 영역 아래쪽에 고정됩니다. 이제 다른 트랙을 스크롤하면서 관심 있는 트랙과 나란히 비교할 수 있습니다. 여러 트랙을 고정할 수도 있습니다.

**11:44**

아래로 스크롤하면 시스템의 CPU 코어별로 나눈 데이터가 보입니다. 그리고 Solar System Mac 프로세스 자체의 트랙도 있습니다. 여기에는 CPU 사용률 요약뿐 아니라 앱 생명주기 이벤트도 표시됩니다. Dock에서 앱을 클릭해 전면으로 가져온 시점이 보입니다.

**12:02**

CPU 사용률이 치솟는 구간에 수상한 빨간 영역도 있습니다.

**12:07**

마우스를 올려 보니 레이블에 Spinning이라고 표시됩니다.

**12:11**

Spinning은 Instruments에서 메인 스레드가 막힌 상태를 가리키는 표현입니다. Mac에서는 이 상태 때문에 회전 대기 커서가 나타납니다. 메인 스레드의 용도는 몇 가지로 매우 명확합니다. 사용자 입력을 처리하거나 UI를 갱신하는 데 사용해야 합니다. 여기서는 분명 다른 일이 벌어지고 있습니다.

**12:29**

메인 스레드를 살펴보겠습니다.

**12:32**

Time Profiler 트랙 아래의 Points of Interest 트랙에 코드에서 추가한 관심 영역들이 나타났습니다. Signpost 구간의 이름에 해당하는 Setup Scene 행이 있고, 여러 관심 영역이 연이어 기록되어 있습니다.

**26:29**

이렇게 많을 줄은 몰랐습니다. 몇 개 정도일 것으로 예상했습니다.

**26:32**

각 영역에 마우스를 올려 개수를 셀 수도 있습니다. 또는 Detail 뷰를 활용할 수도 있습니다.

**26:40**

클릭하고 드래그해서 이 구간을 선택한 다음, Points of Interest 트랙을 클릭해 Detail 뷰에 해당 트랙의 요약을 표시하겠습니다.

자세히 보니 이 구간에서 Setup Scene이 총 여덟 번 발생했고, 한 번에 평균 약 200밀리초가 걸립니다. 다른 Detail 뷰도 있습니다. Jump Bar를 클릭하고 관심 영역 목록을 선택하면 이 트레이스에 기록된 모든 관심 영역을 시간순으로 볼 수 있습니다.

Duration 열에는 각각의 지속 시간이 표시됩니다. 모든 구간이 약 210~220밀리초로, 완료하는 데 걸리는 시간이 매우 비슷합니다.

**27:35**

정말 이상하네요. 왜 비슷한 양의 작업을 계속 반복하는 걸까요? 어떤 이유로 중복 호출되는지 알아보기 위해 Setup Scene을 호출한 쪽을 보겠습니다. 가장 좋은 방법은 Time Profiler가 기록한 호출 그래프를 살펴보는 것입니다.

창 오른쪽 아래의 스택 뷰를 다시 활용하겠습니다. 이번에는 Setup Scene을 호출하는 Prepare Scene 함수를 보겠습니다.

**28:05**

두 번 클릭하면 소스를 볼 수 있습니다.

**28:08**

Prepare Scene은 Setup Scene을 한 번만 호출하는 것 같습니다. 그렇다면 반복의 근본 원인은 여기가 아닙니다.

**28:16**

전체 호출 그래프를 다시 보도록 Jump Bar의 Root를 클릭해 호출 그래프의 루트로 돌아가겠습니다.

**28:24**

스택을 더 위로 올라가 보겠습니다. 그다음 호출자를 선택하니 `for` 루프가 보입니다. 지금 본 반복 현상의 원인일 가능성이 매우 높습니다.

**28:39**

좀 더 자세히 보도록 Xcode에서 이 코드를 열겠습니다. Jump to File in Xcode 버튼을 사용하겠습니다.

**28:51**

Xcode가 열리고 `for` 루프가 표시됩니다.

**28:56**

이 함수가 기억납니다. Update with Planets 함수는 다시 불러오기 작업의 일부로 서버가 보낸 데이터를 받습니다. 그런 다음 새 데이터가 있는 각 행성에 대해, 필요한 경우 앱 내부의 해당 행성 모델을 갱신합니다.

**29:15**

그런데 여러 행성의 갱신 정보가 하나의 데이터 덩어리로 들어올 수 있습니다. 지금은 갱신해야 하는 행성마다 Prepare Scene을 호출하고 전체 뷰를 다시 그리는 것 같습니다.

**29:30**

트레이스를 보면 장면을 다시 그리는 비용이 행성의 내부 모델만 갱신하는 비용보다 훨씬 큽니다. 따라서 내부 모델의 갱신을 모두 모아 처리한 다음, 전체 갱신이 끝났을 때 장면을 한 번만 다시 그려야 합니다.

**29:51**

아주 간단한 수정처럼 보일 수 있습니다. 하지만 저희 경험상 새 기능을 추가하거나 관련 없는 버그를 고치면서 이런 유형의 성능 문제가 코드에 많이 들어옵니다. 이런 버그가 고객에게 전달되지 않도록 하는 좋은 방법은 해당 기능을 정기적으로 실행하는 테스트를 작성하는 것입니다.

**30:11**

시간을 절약하기 위해 다시 불러오기 기능을 실행하는 XCTest를 미리 작성해 두었습니다.

**30:18**

테스트 왼쪽의 이 버튼을 클릭하면 보통은 테스트만 실행됩니다. 하지만 보조 클릭을 하면 Profile 액션이 나타납니다. 이 액션은 Xcode가 테스트를 빌드하고 Instruments 아래에서 실행하도록 지시합니다.

**30:36**

Time Profiler 템플릿을 선택하고 트레이스 녹화를 시작하겠습니다. 이 테스트에서는 다시 불러오기 작업을 `measure` API 호출 안에 넣었습니다.

`measure` API는 여러 번 반복 측정하기 위해 작업을 여러 차례 실행합니다. 측정이 재현 가능하고 일관적인지, 아니면 실행할 때마다 편차가 큰지 파악하는 데 매우 유용합니다.

**31:04**

반복 실행이 모두 끝난 것 같으니 녹화를 중지하겠습니다. 핀치 제스처로 Points of Interest 트랙을 확대하겠습니다. 행이 하나 더 생긴 것을 볼 수 있습니다.

**31:21**

맨 아래에는 앞서 코드에 추가했던 Setup Scene 구간이 있습니다. 그 위에는 `measure` API가 제공하는 또 다른 관심 영역이 있습니다. 작업을 반복 실행한 각 회차에 해당하는 구간을 보여 줍니다.

**31:38**

스크롤하면서 눈으로 보니 실행마다 작업의 동작이 꽤 일관적인 것 같습니다. 이제 테스트의 한 회차 안에서 무슨 일이 일어나는지 알아보겠습니다.

**31:50**

클릭하고 드래그하는 대신 트랙의 이벤트나 구간 하나에 정확히 해당하는 영역을 선택하는 편리한 단축 동작이 있습니다. 세 번 클릭하면 됩니다. 그러면 Detail 뷰에 선택한 영역의 정보가 표시됩니다.

**32:06**

자세히 보니 지금은 Setup Scene 호출이 한 번만 있습니다. 이 의미를 생각해 보세요. Signpost로 얻은 정보를 이용해 CPU 시간 사용량을 약 한 자릿수 규모, 즉 10배 정도 줄였습니다.

**32:23**

방금 살펴본 개념을 정리해 보겠습니다. Time Profiler가 수집하는 통계적 프로파일은 어떤 코드가 가장 흔하게 실행되는지 보여 주는 데 매우 유용합니다. 하지만 코드가 어떻게, 왜 실행되는지를 보여 주는 Signpost API의 측정을 대신할 수는 없습니다.

**32:54**

테스트를 이용해 작업을 안정적으로 반복 재현하고, 개발 초기부터 자주 프로파일링하는 것이 얼마나 유용한지도 확인했습니다.

**33:07**

오늘은 주로 CPU 사용량이 많거나 부적절한 곳에서 CPU를 사용하는 데서 발생하는 성능 문제를 조사했습니다. 하지만 Instruments에는 다른 종류의 자원 사용에 관한 성능 질문에도 답할 수 있는 여러 템플릿이 있습니다. 파일과 디스크 사용을 위한 템플릿이 있습니다.

**33:26**

네트워크 사용을 위한 템플릿도 있습니다. 앱과 운영체제 또는 운영체제에서 실행 중인 다른 프로세스 사이의 상호작용을 이해하는 데 도움을 주는 템플릿도 있습니다. 여기서 끝이 아닙니다.

Instruments에는 Custom Instruments 같은 고급 기능도 있습니다. 예를 들어 프레임워크 개발자라면, API 사용자가 프레임워크 사용 방식에 관한 성능 질문에 답할 수 있도록 Custom Instruments 패키지를 제공할 수 있습니다.

또한 Instruments 앱의 여러 Instrument를 조합해 특정 성능 질문에 답하도록 사용자 정의 템플릿을 만들 수도 있습니다.
